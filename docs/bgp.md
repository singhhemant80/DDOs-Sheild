# Shield's BGP speaker

Shield announces blackhole routes with its own FRR (`bgpd`), installed on the Shield server by the
installer. Sessions marked **staging** (lab routers) are configured as soon as the speaker is FRR.
Sessions marked **production** are configured only once production is switched on, and carry real
blackholes only after an acceptance run: see [production.md](production.md).

Nothing changes until you choose it: the `bgp_speaker` setting stays `simulated` (nothing leaves
Shield) until an administrator switches it to `frr`. Switching is refused while any mitigation
action is open, so no route is left stranded on the old speaker.

## What Shield configures in FRR

Shield owns the BGP configuration of this FRR and touches nothing else. For every enabled,
Shield-managed staging session:

| | |
|---|---|
| Inbound | `route-map SHIELD-DENY in`: Shield accepts no routes from anyone |
| Outbound | `route-map SHIELD-OUT-<peer> out`: only prefixes in that peer's own prefix-list leave, with the peer's blackhole communities, `no-export`, and a discard next hop (`192.0.2.1` / `100::1`, or the provider's required next hop); everything else is denied |
| Limit | `maximum-prefix-out` from the session's route limit; the speaker also refuses to add more |
| Session | remote AS, port, eBGP multihop, update-source, optional TCP-MD5 password (stored encrypted), connect retry 10 s |

Each approved announcement adds the prefix to that peer's prefix-list plus a `network` statement;
withdrawal removes both. Verification reads FRR's **advertised routes per session** and requires
the prefix to be there with the discard next hop; a session that is down fails verification, and
the action fails and is rolled back after 60 seconds.

## Four independent layers that stop an unauthorised blackhole

1. **Planner** (preview, proposal, approval, just before execution): protected prefix, ownership,
   scope, own infrastructure, opt-outs, emergency stop, provider policy, limits, sessions.
2. **Database**: an action's target must be inside an enabled protected prefix (trigger).
3. **Speaker**, independently of the planner: the action must exist and be executing or active;
   the prefix must equal its target, be inside a protected prefix that allows blackholing and be
   no broader than allowed; the session must be a Shield-managed session that is allowed to carry it (staging, or accepted production); communities and
   next hop must match the peer's current policy. Every FRR command is built from parsed values
   and checked against a strict character set (vtysh would otherwise run a newline as a second
   command).
4. **Your router's import filter**, generated by Shield (BGP sessions → Router filter, or
   `GET /api/v1/bgp/receive-filter?format=routeros|frr`): accepts only routes inside protected
   prefixes that allow blackholing, no broader than each allows, carrying the internal blackhole
   community; rejects everything else. Even a compromised Shield cannot blackhole anything else.

## Setting up a staging lab

1. Settings: set `internal_blackhole_community` (e.g. `65535:666`) and `bgp_router_id` (an IPv4
   address of the Shield server).
2. BGP sessions → Add session: purpose *Internal blackholing*, peer = your lab router, Shield's
   address, both AS numbers, a route limit, environment *staging*.
3. Router filter: put the generated filter on the lab router's session from Shield, and route the
   discard next hop to null (RouterOS: the filter sets `blackhole`; FRR: `ip route 192.0.2.1/32 Null0`).
4. Settings: `bgp_speaker` = `frr`. Within 30 seconds the session should show *Established*.
5. Blackhole a test address from the Mitigation center and check it on the router.

For a provider's blackhole service, add a session with purpose *Provider blackhole service*; it uses
that upstream's verified blackhole policy (communities, next hop). Keep it staging until it has been tested, then follow [production.md](production.md).

## Tested

`backend/tests/test_frr_staging.py` runs Shield's FRR against FRR lab routers (19 tests, also in CI):

- an authorised /32 reaches the lab router with `65535:666 no-export` and the discard next hop,
  and is withdrawn;
- routes injected straight into Shield's FRR (bypassing Shield: a /24, a /25, an address outside
  protected space, a protected /32 without the community) are all rejected by the generated
  router filter;
- Shield's outbound filter does not send a prefix that is not in the peer's list;
- the speaker refuses: missing or unknown action, prefix different from the action, malformed
  prefix (including an embedded newline), changed policy communities, unknown peer, a prefix that
  no longer allows blackholing; FRR's configuration is unchanged after each refusal;
- a session that is down: the action fails and is rolled back;
- FRR restarted with an empty configuration: reconciliation restores sessions and routes;
- production sessions are not configured while production is off, and the plan says so; the speaker cannot be switched
  while actions are open; provider sessions carry the provider's communities.

Lab run with the real collector, detector, controller and FRR (loopback only):

| Step | Result |
|---|---|
| Session to the lab edge router | Established 2 s after configuration |
| Synthetic UDP flood | Policy proposed internal blackholing 44 s later |
| Approve | Announced and verified as advertised in 1.1 s |
| Lab edge router | Has 163.5.191.20/32, `blackhole no-export`, next hop 192.0.2.1 |
| /24 and an unprotected /32 injected straight into Shield's FRR | Lab router kept only 163.5.191.20/32 |
| Shield's FRR killed and restarted empty | Route withdrawn, restored by reconciliation 13 s later |
| Withdraw | Gone from the lab router |

**Checked on RouterOS 7.25** (MikroTik CHR in QEMU, `lab/routeros` on the `lab/routeros-chr` branch,
run by GitHub Actions): the generated filter and connection were pasted as generated, the session
with an FRR announcing like Shield came up, and the router installed only the authorised /32
(`163.5.191.250/32`, flags `AbB`: active, BGP, blackhole); the /24, an address outside protected
space and a /32 without the community were all filtered. The removal commands left nothing behind.
Findings that changed the generator:

- RouterOS 7.20+ requires `instance=` on a BGP connection; the script now uses the router's existing
  instance for its AS (and shows the pre-7.20 form as a comment).
- The internal community must be a standard community; `154950:666` does not exist (4-byte AS).
